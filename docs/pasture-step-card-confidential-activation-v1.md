# 步道卡 · 一卡一码保密激活机制 V1

## 不变原则

1. **邮箱注册不代表已激活步道卡**。验证邮箱只开放牧场景观、捏羊、抓羊和昼夜天气。
2. **卡面六维、卡号和二维码不等于密码**。公众可看见卡面，但不能推算密钥。
3. **一码仅限激活一次**。每一份数字或实体步道卡都拥有独立密钥，一份凭证不能重复兑换，一位居民最多绑定一张当前有效的卡。
4. **失败时必须关闭权限**。没有生产密钥、没有数据库、密码不正确或密码已使用，都不能提前放开「我的牧草」。
5. 激活是解锁功能的资格，不是新的登录方式。已经激活仍需使用本人邮箱会话。

## 发行权归属：仅限步道事工

**步道事工是数字卡和实体卡的唯一发行主体。**

- **在线申请**：注册居民仅能提交申请；提交、审核通过、领取展示三个动作不等于发行。申请必须经步道事工拥有发行权限的同工审核批准，留下授权依据，事工才能为指定居民生成和发放卡密；指定居民之外的账户不能兑换这张定向卡。
- **步道现场**：带领同工可从事工预先批准的现场发行批次中发放数字卡密或实体凭证。公开领取者尚不确定时，采用由事工发行的未绑定卡；首次有效兑换后绑定。领到密码并不意味着已激活。
- **任何个人没有发行权**：用户不能自行生成有效卡、自动从注册奖励中领取卡、绕过审核获得卡密，也不能代表步道事工批量发行或转售。申请界面将来也只能记录待审申请，不得调用签发模块。
- **组织内最小权限**：审批资格、卡密生成资格、密钥保管与撤销权限应授予事工指定人员，留有发行人标识、批准依据、渠道、批次和领取绑定记录。取得一个普通牧场账号不能拥有发行资格。
- **发放渠道 ≠ 发行主体**：线上申请批准后交付和步道现场交付使用同一密钥服务器；`ONLINE` / `TRAIL` 只区别流程，不改变唯一发行主体。
- **尚未完成的部分**：线上申请表、同工审核界面、自动定向交付和线上身份授权尚待建设；目前只存在受控离线发行工具。不得将技术性的离线工具等同于已经完成的事工发行管理后台。

### 统一生命周期

`DRAFT_APPLICATION → APPROVED_BY_MINISTRY → ISSUED_BY_MINISTRY → DELIVERED → ACTIVATED`

线上申请走全链路；步道现场可以先按事工活动审批产生 `TRAIL` 批次，再现场交付。只有 `ISSUED_BY_MINISTRY` 后的有效秘密才能用于兑换。申请被拒绝或未审批不产生任何有效密码。

## 密钥规则

- 格式：20 个 Crockford Base32 随机字符，以 5-5-5-5 分组展示或印制，随机强度约 100 比特。
- 卡面公共编号格式为 `BD-` 加 10 个随机字符。花色、棋子、骰子、数字、Logo 位置和公共编号绝不能作为密钥生成种子。
- 所有密码均由密码学安全随机源生成，服务器只保存独立生产秘密 `PASTURE_CARD_PEPPER` 保护下的 HMAC-SHA-256 摘要；不能储存明文密码。
- 生产密钥不得进入代码库、聊天、网页、二维码、用户端缓存或普通日志。
- 服务端验证记录激活状态、发行批次、绑定居民；不返回「不存在 / 已被用过」的区别。
- 15 分钟最多尝试 5 次，持久化计数在数据库中；另有 IP 层限流。

## 数字优先、实体兼容：同一凭证体系

步道卡不是必须存在于实体卡片上的密码。数字卡（类似电子充值卡密）和实体收藏卡是两种交付形式，不是两套权限系统：均由同一服务器发行、核验、一次性兑换和绑定。公开的六维卡面、数字收藏卡及公共卡号均不能推导一次性密钥。

### 数字卡：推荐优先实现

- 只有步道事工可以定向发行数字卡密。用户可申请领取，但申请不会自动生成卡密；事工批准后向指定居民安全交付。用户不可自行发卡或未经授权转售。激活后不允许转让账户权限。
- 当前离线发行工具已经支持输出一次性卡密资料；**尚未实现自动在线发放、在线购买、赠送、收件箱、付费或订单系统**。数字交付必须额外建设经过授权的领取页面，不能把管理员临时导出文件当作公共 API。
- 正式电子发放时，优先采用登录后的专属领取页、短时且一次性揭示以及严格的后台授权；不要在公开链接、二维码、浏览器日志、查询字符串或公开邮件里暴露卡密。任何负责延迟交付的系统都需设计独立的受控加密暂存和领取审计，不能要求从不可逆 HMAC 摘要恢复明文。
- 「数字卡」激活后只显示可公开的六维形象、卡号、激活状态与所属居民，不再显示原始兑换码。

### 实体卡：可选的收藏或赠送载体

已确定的钥匙扣型六维卡仍然可以制作，但**永久展示的卡面不要公开密钥**。若需要预印激活码，可用另附密封小纸套或经测试的防拆刮涂层，与公共卡号受控配对。

第三方印厂原则上只接触公开卡面文件；任何密码打印和封装过程都必须有相应保密、清点和销毁规定。泄漏或密封破损的未兑换卡应直接撤销。

所有交付形式的公开二维码只用于打开激活入口，可带公共编号，但**不可包含任何可用于直接兑换的秘密**。

## 激活与数据绑定

1. 已验证邮箱、有本人羊的居民进入唯一开放的「步道卡」功能区。
2. 输入从数字卡安全领取或实体卡密封交付的 20 位一次性代码；用户端用 HTTPS POST 向服务端提交。
3. 服务器验证邮箱 session、居民羊、数据库限流与 HMAC 摘要。
4. 数据库一次性执行从 `ISSUED` 到 `ACTIVATED` 的状态变化，并将居民的 `card_activated_at` 置为有效。唯一约束防止同一卡并发领取、一个居民同时激活多卡。
5. 重新从服务端读取身份，只有明确返回 `cardActivated: true` 才可进入「我的牧草」。
6. 其余在建板块仍然锁定。

## 丢失、撤销、再发行

- 未兑换的数字卡密泄漏或实体卡丢失：持有秘密的他人可能抢先兑换，必须撤销并换发；公开卡号不等于秘密。
- 已激活后的电子截图或实体卡遗失：原密码不能再次使用；他人仍需对应邮箱登录才能接触个人古卷。
- 撤销：后台离线操作将卡改为 `REVOKED` 并撤销对应用户的 `card_activated_at`。
- 再发行：人工核实身份与撤销原因后发新卡；永不找回或重发旧密码。
- 密钥轮换需要保留多版本验证密钥或安排未兑换卡重新发行；直接更换密钥会让旧批次失效。

## 仅限授权管理员的离线操作

发行程序 `scripts/pasture-card-admin.js` 与公开 API 严格隔离。需要数据库凭证和独立 `PASTURE_CARD_PEPPER`，无通用密码和默认管理员。

发行命令（只能在经授权的事工环境，由 `PASTURE_MINISTRY_ISSUER_ID` 对应同工执行）：

- 线上定向发行：`node scripts/pasture-card-admin.js issue --count 1 --batch <批次> --channel online --issuer <发行人> --approval-ref <批准记录> --recipient <居民UUID> --out <仓库外绝对路径> --confirm-issue`
- 步道现场批次：`node scripts/pasture-card-admin.js issue --count <1..200> --batch <批次> --channel trail --issuer <发行人> --approval-ref <活动审批记录> --out <仓库外绝对路径> --confirm-issue`
- 撤销：`node scripts/pasture-card-admin.js revoke --issuer <发行人> --serial <BD-...> --confirm-revoke`

当前命令通过独立的生产数据库凭证、`PASTURE_CARD_PEPPER`、`PASTURE_MINISTRY_ISSUER_ID` 及批准记录识别执行者；**生产中仍应进一步施加数据库账户最小权限、人员审批、密钥隔离与审计制度**。仅有文本形式的 `--approval-ref` 不代表后台真的完成了审批，不得提前称为自动审批。

发行明文只写入管理员指定、权限为 `0600` 的仓库外暂存文件，可在严格授权下用于数字卡交付或实体卡密封制备；不写 GitHub 或 Vercel 构建日志。发放或印制后按机构保密流程销毁暂存文件；权限 0600 不等于加密，需妥善保管。
