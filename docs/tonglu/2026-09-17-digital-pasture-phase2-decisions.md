## 1. 阶段2的产品精神

阶段2不是把阶段1的像素牧场继续“加功能”，而是开始建立一种完整的基督徒数字生活方式。

两条最高级别产品句正式固定：

> **喜乐、关系、陪伴、生活、等待、给予、一起走路。**

> **让基督徒第一次拥有一种令人羡慕的数字生活方式。**

目标不是制作一个带有宗教皮肤的 App，也不是把灵修、群聊、活动、代祷、打卡等传统功能重新包装，而是让这些真实的信仰关系自然发生在一片有生命的数字牧场中。

数字牧场希望成为“下一个时代基督徒的一种时髦的小游戏”：打破外界以及基督徒自身对于基督徒数字产品的刻板印象，让信仰生活更喜乐、更有关系感，也让基督徒拥有美好的数字人生。

这里的“小游戏”不是把信仰娱乐化，而是建立一种轻盈、可爱、愿意每天回来看一眼、同时真实承载牧养与同行关系的数字生活世界。

---

## 2. 公共牧场的基本交互定义

公共牧场首先是**视觉世界**，其次才是关系操作界面。

它不是用户列表，不是朋友圈，不是论坛，不是聊天室，也不是信息流。

原则：

> **信息不是被“发布”出来，而是变成牧场里正在发生的事情。**

因此：

- 需要可以表现为羊的柔和呼唤声波。
- 牧养可以表现为树上的风铃曾经响过。
- **牧草来自用户自己的真实灵修与读经。**
- **灵粮来自系统推送，属于与个人牧草不同的一类喂养内容。**
- 给予可以表现为羊在草地上留下愿意送出的东西。
- 活动与出发可以表现为路、木板、移动与聚集。

公共牧场要让用户产生的第一反应是：

> **今天这里发生了什么？**

而不是：

> 我今天还有哪些任务没有完成？

## 3. 用户每日核心循环（顺序已确认）

阶段2的每日体验形成以下三段式循环：

### 第一段｜先回到自己的羊

用户进入同路后，第一件事是回到自己的数字羊。

核心动作：

> **通过自己的灵修来喂养羊。**

当前明确的一项真实来源是：**读经记录**。

个人真实灵修与读经，在数字牧场中的对应物是：**牧草**。

因此，数字羊的“被喂养”不是虚拟点按，也不是签到，而应来自用户真实的灵修行为。

这一层的含义是：

> 我先照顾自己的生命，再进入共同体。

### 第二段｜看“今日发生”

完成或查看自己的生命状态之后，用户进入“今日发生”。

这里不是信息流，而是今天牧场中值得参与的一两件或少量事情。

目的：

> **看看今天有什么是我可以参与的。**

可能包括：某只羊发出需要、某次与自己相关的出发、某个给予正在发生、某个关系事件或牧养痕迹等。

### 第三段｜进入牧场，自然遇见

在“自己的羊”和“今日发生”之后，用户再进入公共牧场。

这里不要求用户完成某件事，而是：

> **看牧场，自然遇见。**

因此，阶段2每日循环正式固定为：

> **回到自己的羊 → 用真实灵修产生牧草并喂养羊 → 看今日发生并决定是否参与 → 进入公共牧场自然遇见。**

## 4. 身份体系：老用户与新用户

### 4.1 老用户

历史中已经参加过多次真实步道、已经被现实关系验证过的老用户，不需要再次通过步道卡证明“是真人”。

采用 A1：

> **历史用户导入后，自动生成 Budao ID，自动生成数字羊，并直接进入公共牧场。**

未来仍然会获得一张步道卡，但：

> **老用户：先有羊，后领卡。卡是绑定，不是激活。**

### 4.2 新用户

新用户路径：

> **网络注册 → 生成 Budao ID → 生成数字羊 → 尚未真人验证 → 获得步道卡 → 输入卡上唯一激活码 → 真人验证完成 → 正式进入公共牧场。**

对新用户：步道卡承担真人验证与激活作用。

### 4.3 统一底层原则

步道卡定义为：

> **现实真人验证与现实身份识别的一种机制。**

永久身份核心仍然是：

- Budao ID
- Sheep ID

卡、手机号、邮箱等均为可替换凭证。

## 5. 当前设计原则

1. **信仰真实行为优先于游戏内虚拟操作。** 羊的生命状态应尽可能来自真实读经、真实同行、真实给予、真实关怀，而不是纯虚拟点数。
2. **世界化优先于 App 化。** 能成为牧场里的对象、动作、天气、距离、痕迹，就不要做成按钮、列表、徽章或 dashboard。
3. **喜乐不等于娱乐化。** 游戏语言服务于生命与关系，不以成瘾、等级、稀缺皮肤、排行榜为目标。
4. **先自己，再关系，再世界。** 每日循环的顺序已经固定为：自己的羊 → 今日发生 → 公共牧场。
5. **公共牧场不是内容消费场。** 它是一个持续存在、可进入、可偶遇、可留下关系痕迹的数字生活世界。

## 6. 个人灵修、牧草与灵粮：三者必须严格区分

### 6.1 个人灵修 / 读经 → 牧草

正式选择：**线下自己读，系统中记录。**

同路不要求用户必须在系统内阅读全文，也不试图取代纸质圣经或其他读经工具。

用户可以在线下使用：

- 纸质圣经
- 其他圣经 App
- 小组读经材料
- 自己长期使用的读经方式

完成真实阅读后，回到同路记录自己的读经段落；这份真实读经在数字牧场中的对应物是：**牧草**。

固定原则：

> **个人灵修读经是牧草。**

> **现实中读经，数字牧场中长出牧草。**

> **系统记录的是“这只羊今天读了哪一段”，而不是强迫用户必须在同路里读完文字。**

因此：

> **真实读经 → 记录经文段落 → 形成牧草 → 羊获得喂养。**

### 6.2 系统推送 → 灵粮

“灵粮”不再用于指代用户自己的读经进度或由读经产生的牧草。

正式固定：

> **系统推送是灵粮。**

灵粮是由系统、牧养者或未来指定内容机制送到这只羊面前的一份内容性喂养；它与用户自己通过读经形成的牧草是两种不同来源、不同语义的喂养。

因此必须严格避免混用：

- **牧草 = 自己真实灵修 / 读经的世界化结果。**
- **灵粮 = 系统推送给这只羊的内容。**

阶段1已经锁定的“一份灵粮，一次开启；打开以后即消失，不进入历史记录，不提供再次查看”的规则继续保留，除非阶段2后续另行修改。

当前尚未确定：灵粮是否也影响羊的视觉活力、是否影响牧草量，或完全作为独立的牧养内容存在。此项不得擅自合并。

### 6.3 读经记录方式：采用 A

正式选择：**A｜记录“今天读了哪一段”。**

例如：

- 约翰福音 6:1–21
- 诗篇 23
- 创世记 1:1–5

记录模型必须支持**跳读**。系统不得假设用户必须按圣经顺序连续阅读，也不得把“读到哪里”当作唯一进度模型。

用户可以今天读诗篇，明天读约翰福音，后天回到创世记；这些都属于正常、有效的真实读经记录。

### 6.4 牧草不按阅读量计量

这是阶段2的重要固定原则：

> **读多少都一样。**

只要用户真实完成了一段读经并记录下来，这一天就产生有效的牧草喂养事件。

系统不得建立以下映射：

- 读得多 → 草更多
- 读得少 → 草更少
- 章数更多 → 羊更强壮
- 节数更多 → 获得更多成长值
- 阅读量 → 属灵程度

因此单次读经是**非量化的生命事件**，不是按篇幅计分的资源系统。

固定句：

> **喂养只回答“今天是否真实吃到了草”，不回答“今天吃了多少草”。**

用户一天可以记录一段或多段经文；系统可以保存真实阅读记录，但这些记录数量不得换算成更高等级、更丰盛奖励或更强的羊。

### 6.5 羊的视觉活力由牧草量驱动

固定原则：

> **羊的视觉活力与牧草的多寡有关，并采用指数型关系，而不是线性关系。**

这里必须与“读多少都一样”严格区分：

- 单次读经的篇幅、章节数、节数，不决定得到多少牧草。
- 读一小段与读很多章，不产生“多读多草、少读少草”的差别。
- 牧草来自真实灵修 / 读经事件，而不是阅读字数奖励。
- 羊的视觉活力读取的是**当前牧草量**，不是当天阅读篇幅。

因此系统存在两个彼此分开的层次：

> **真实读经行为 → 牧草。**

> **当前牧草量 → 以指数型关系影响羊的视觉活力。**

“视觉活力”应表现为世界内的生命状态，例如动作频率、步伐、姿态、主动探索、吃草、轻跳、靠近其他羊等，而不是数值面板、等级、战力或属灵评分。

这条机制的目的不是评价人的属灵程度，而是让真实灵修在数字世界中持续产生可感知的生命反馈。

### 6.6 下一项必须定义：牧草生命周期与灵粮作用

下一步需要分别确定两件事：

1. **牧草如何产生、积累、消耗或自然变化。**
2. **系统推送的灵粮是否参与羊的视觉活力，还是完全独立于牧草系统。**

在这两个问题确定以前，牧草与灵粮不得在数据层或视觉层被合并为同一种资源。
