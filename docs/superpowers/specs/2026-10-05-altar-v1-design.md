# 祭坛 V1 架构设计

日期：2026-10-05

## 1. 目标

为步道网站新增最高监管层“祭坛”。祭坛不是传统后台，而是建立在 Tent 之上的独立监管空间，用于让最高等级用户查看所有带领人发布的路线，并对异常或需要干预的路线执行监管动作。

核心产品原则：

- 带领人拥有路线。
- 日历拥有时间。
- Slot 只负责展示。
- 祭坛拥有监管状态。

祭坛不得成为正常发布链路的单点依赖。即使祭坛暂时不可用，带领人仍应可以正常登录 Tent、创建/修改自己的路线，并完成既有发布流程。

## 2. 入口与可见性

### 2.1 唯一入口

祭坛唯一入口位于 Tent 登录成功后的内部主入口空间右下角。

入口不是第四个菜单项，也不与“步 / 道 / 祷”并列，而是一块几乎融入地面的房角石。

### 2.2 可见性规则

V1 中，仅 `tony` 账户登录成功后可见房角石入口。

其他带领人：

- 不显示房角石；
- 不显示“祭坛”文字；
- 不暴露监管入口；
- 不获得祭坛 API 权限。

前端隐藏只用于体验，真正权限必须由服务端校验，不能依赖 DOM 隐藏或用户名的客户端判断。

### 2.3 交互

默认状态：房角石极低对比度、无文字、无发光、无权力象征。

Hover / focus 时：只出现极淡的“祭坛”二字。

点击后进入独立祭坛空间。

移动端：入口同样位于 Tent 内部页面最下方右侧，以小石块形式存在。

## 3. 视觉与美学

祭坛沿用 Tent 的世界观、材质、排版、空间感和交互节奏，不建立一套新的“企业后台”视觉语言。

关键词：

- 房角石
- 卑微
- 安静
- 沉重
- 克制
- 不显权力感，只显托付感

禁止：

- 传统 Dashboard 风格；
- KPI 卡片；
- 饼图；
- 高饱和状态标签；
- 显眼的 ADMIN 标识；
- 与 Tent 脱节的现代后台 UI。

祭坛内部第一版以“石案”为核心视觉：路线像刻在石面上的记录，监管动作只在打开某条路线后出现。

## 4. 权限模型

V1 建立三层概念权限：

1. 参与者：公开浏览、报名、使用公开功能。
2. 带领人：登录 Tent，仅管理自己的路线。
3. steward：可进入祭坛、查看全部路线并执行监管动作。

V1 实际授权对象为 `tony`。

实现时应避免把最高权限仅写死在前端。服务端认证应能表达“publisher + steward”能力，即同一个 Tony 账号既可作为带领人发布自己的路线，也可进入祭坛监管全局。

## 5. 祭坛 V1 功能范围

### 5.1 全路线列表

祭坛显示所有带领人的路线，不限当前三个公开 Slot。

每条路线至少显示：

- routeId
- 带领人 / leaderId
- 路线名称
- 活动日期
- 集合时间
- 发布时间
- 最后修改时间
- 当前监管状态
- 日历状态
- 当前是否进入公开展示

### 5.2 基础筛选

V1 只保留：

- 全部
- 未来
- 已结束
- 待处理
- 已撤下

### 5.3 路线详情

点击路线后，在同一祭坛空间展开完整资料，包括：

- 路线事实；
- 带领人身份；
- 发布时间与修改时间；
- 日历映射状态；
- 当前公开展示状态；
- 监管状态；
- 后续审计记录。

### 5.4 监管动作

V1 支持：

- 退回修改
- 暂停展示
- 锁定
- 恢复

不提供“永久删除”。所有监管动作必须留痕。

## 6. 数据边界

### 6.1 routes.json

`routes.json` 继续只保存路线事实和带领人归属，不保存瞬时 Slot 投影，也不混入祭坛监管状态。

### 6.2 监管数据

新增独立监管状态存储，按 `routeId` 关联，例如：

- status
- locked
- reviewedBy
- reviewedAt
- reason
- updatedAt

具体文件/存储形式在实施计划阶段确定，但必须保持与路线事实解耦。

### 6.3 审计

每次祭坛动作必须形成不可静默覆盖的审计记录，至少包含：

- action
- routeId
- actor
- timestamp
- reason / note（如适用）

后续可以扩展为版本对比，但 V1 不强制做完整 diff 系统。

## 7. 服务端边界

祭坛所需的“查看全部路线”“读取监管状态”“执行监管动作”均必须通过服务端权限校验。

禁止：

- 只在前端判断 `username === "tony"` 后直接调用无保护接口；
- 在浏览器端放置管理员口令；
- 通过隐藏链接代替授权；
- 让普通 publisher 会话访问全量监管数据。

## 8. 与现有主链的关系

现有主链：

带领人登录 → Tent → 路线校验 → leader-owned route → 日历 → 动态 Slot 投影 → 公开步道页

祭坛应位于这条链之上：

- 读取全量路线；
- 读取/写入监管状态；
- 必要时影响“是否允许公开展示”或“是否允许继续修改”；
- 不改变路线所有权；
- 不把 Slot 重新变成身份；
- 不破坏既有 Tent 发布流程。

## 9. 状态语义

V1 建议使用以下监管状态：

- active：正常
- needs_changes：退回修改
- paused：暂停公开展示
- locked：锁定
- restored：恢复后重新进入正常状态（实现时可归一为 active + audit）

其中 `locked` 更适合作为独立布尔状态，以避免与展示状态互相冲突。最终字段模型在实施计划中确定。

## 10. 错误与安全行为

- 非 steward 请求祭坛页面数据：403。
- 非 steward 调用监管动作：403。
- routeId 不存在：404。
- 重复动作：应尽量幂等。
- 对已结束路线的监管动作：允许记录，但不应破坏历史事实。
- 监管系统故障：不应导致 Tent 正常发布链整体不可用。

## 11. 测试要求

至少覆盖：

1. Tony 登录后服务端识别 steward 权限。
2. 普通带领人不能访问祭坛 API。
3. 普通带领人前端不显示房角石。
4. Tony 登录后显示房角石。
5. 祭坛读取所有 leader-owned routes，而不是只读取三个 Slot。
6. 暂停路线后公共展示层不再展示该路线，但 canonical route 仍保留。
7. 恢复后可重新展示。
8. 锁定后带领人不能修改该路线。
9. 所有监管动作产生审计记录。
10. 现有 leader login / publish / calendar / projection 回归测试继续通过。

## 12. V1 明确不做

- 报名人数统计
- 举报系统
- 消息中心
- KPI/数据图表
- 自动风险评分
- 多管理员协作
- 完整历史版本 diff
- 永久删除路线
- 修改现有首页动画或数字牧场

## 13. 成功标准

V1 成功的最低标准：

- Tony 使用同一个账户登录 Tent；
- 只有 Tony 在 Tent 右下角看见不起眼的房角石；
- 点击进入祭坛；
- 能看见所有带领人的路线；
- 能打开任一路线查看详情；
- 能执行退回、暂停、锁定、恢复；
- 操作有服务端授权与审计留痕；
- 普通带领人既看不见入口，也无法越权访问；
- 现有 Tent → route → calendar → slot → public page 链路继续稳定。
